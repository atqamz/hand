# Hand — personal spec

Hand is the operator's personal tool for running a crew of agents through one supervisor. It is not a product for other users. Every decision is judged by one question: does this make the operator's daily loop cheaper, more deterministic, or more reliable?

Written 2026-09-26 after freezing the v19 rewrite. The runtime was chosen the same day after two spikes: Orca (`~/orca-spike/REPORT.md`) and Luvus (`~/luvus-spike/REPORT.md`).

## Why this exists

The operator evaluated kunchenguid/firstmate (same concept: one liaison agent running a crew in worktrees) and rejected it: it burns tokens and depends on too many tools (gh-axi, quota-axi, lavish-axi, …). The parts worth keeping are the supervisor model, fleet memory, and determinism. Hand's own v19 work then drifted into product-grade machinery (multi-platform release qualification, npm/edge publishing, versioned contract manifests, live-cutover proofs, exec-guard attestation) that cost days and tokens without improving the daily loop.

## Core

1. **One supervisor.** The operator talks to a single agent: the managed supervisor, which Hand runs in the background in the fleet's Luvus session and the operator reaches from the board. It captures requests, dispatches workers into isolated git worktrees, watches them, and escalates only decisions that genuinely need the operator. It is a router, not a worker: editing the project's files, running builds, tests, npm or cargo, SSH, deploys and debugging become tasks with worker attempts. It keeps the judgement — the operator's intent and standing rules, the fleet's state, the gates, and the verdict on each report — and writes the briefs, plans and reports; it delegates the evidence: every code change, test, product doc (`docs/`, `README.md`, `AGENTS.md`), PR, independent review and read-only investigation is a worker attempt. A question the committed code can answer goes to a worker whose brief says it only reads; the supervisor reads only what it needs, bounded, or uses a worker whose output it can evaluate. That boundary is a design rule, not a preference.
2. **Fleet memory.** Operator context, project context, and task history are durable outside any chat session. A fresh supervisor orients from Hand state alone, cheaply, without re-explanation.
3. **Determinism.** Workflow state lives in a state machine over SQLite, never in LLM memory. The same state renders the same orientation. Idle costs zero tokens: a watcher wakes the supervisor only when something changed, when a timer it armed comes due, or, on a backoff, when it idles with active work that nothing watches.
4. **Fleets.** A fleet is any folder `hand init` ran in, with an immutable ID and a name the operator can change. The operator runs each fleet's supervisor from its board, and several fleets run side by side. `~/.secondhand` (`$SECONDHAND_HOME`) holds what belongs to the machine: a bookmark from each fleet ID to its folder, every worker worktree, the Board's files. The fleet folder holds its own Luvus copies, backups and model cache, so it can move to another mount. Each fleet has its own Luvus session, watcher and board.
5. **Board.** One place outside chat where everything is visible:
   - every operator request becomes a durable item (inbox/Task) before work starts, so nothing lives only in chat text;
   - one card per Task: goal, status, current plan, attempts, latest report, pending decisions, deliverables;
   - the board is a pure projection of Hand state: deleting or restarting it loses nothing;
   - the board is the operator's interface. It answers a Decision by ID, acknowledges a report by ID, and starts, resumes, stops and chats with the supervisor. Judgement goes to the supervisor through chat, and supervisor control works over loopback only.

## Hard constraints

- **Token-frugal.** Compact output (TOON). `hand orient` has a measured size budget. No LLM polling; event-driven wakes only.
- **Few dependencies.** Required: git, the worker harness CLIs the operator uses (Claude Code, Codex, opencode, Antigravity, GitHub Copilot, oh-my-pi), and Luvus (github.com/RizRiyz/luvus) as the one runtime backend. Hand uses only Luvus's runtime primitives over UHP 1.0: exact-argv terminals, agent status, fenced input, and events. Hand owns state, worktrees and the board itself, and never uses Luvus's task ledger or worktree commands. `gh` is optional. No `*-axi` tools. Hand keeps a pinned copy of a Luvus binary: the operator's, or the release its own build names as tested (`luvus.Tested`, set by hand when a Luvus release is checked against Hand), which `hand update` downloads and checks against its published SHA-256. It never builds one.
- **Upstream.** Every Luvus gap gets a Hand-side guard first. Issues and pull requests to RizRiyz/luvus run in parallel, and a guard is deleted only after the fix ships in a release Hand pins.
- **Linux**, the operator's machine and projects, plus **macOS** and native **Windows** (amd64), which are supported, with the gaps listed in `docs/platforms.md`; `docs/dogfood/` has the checks for a real machine. Neither has units: `hand open` starts the board, which keeps the watchers alive, and a LaunchAgent or a Startup-folder shortcut starts it at login. Windows has no desktop notifications.
- **Board** is `hand board`: a local web page from the same Go binary (`net/http` + `html/template`), with small first-party JavaScript and no framework or build step. One board host serves every fleet at its own path, `/<fleet id>/`. It is a projection of state plus supervisor control, drawn as an on-call board: a 56px rail of icons (a sheet below 900px), and from 900px a work pane beside the supervisor pane with a draggable separator, where the work pane holds Needs (what waits on the operator, in bands by severity, most severe first) and then the tasks with a search, and the supervisor pane holds the supervisor's controls, its conversation and the composer; below 900px the same parts are three tabs. A masthead shows the supervisor's state and its context use against the model's window, and a composer switches its model, effort or harness and interrupts it. Supervisor replies and reports use a small safe markdown subset with tables and linked refs. Decisions are answered from a choice list, in Needs, on the decision's page or in the dialog; from the board, things open in a dialog over the page, where their forms work, and places in place. The board updates itself over server-sent events, and is reachable from a Companion through the Hand app over iroh, or a tunnel such as `ssh -L`. Supervisor control works over loopback only; on a network address only answering decisions and acknowledging reports remain. A Luvus dock may mirror one line per Task; it never replaces `hand board`.

## Non-goals

- Windows on arm64, a Windows service or Task Scheduler integration, and desktop notifications on Windows.
- npm packages or other package managers.
- Versioned contract manifests, DDL relock ceremony, mutation-score gates.
- A deterministic converter from Hand 0.7 data, or a live cutover. `hand init` refuses to make a fleet in a folder holding 0.7 data (`state/hand.db`) and writes nothing; a fleet starts in a folder of its own. A folder that already has `hand.db` is a fleet and is not refused.
- Exec-guard, operator attestation, provider identity proofs beyond what the chosen backend gives natively.
- Features for hypothetical other users.

## Skills

A skill is a **manual**: a sequence of steps an agent follows, with the commands or files each step touches and the stop condition. Facts that only describe a domain belong in `AGENTS.md` or a skill's `references/` folder, and a skill that is only a reading list is moved there or dropped. `hand skills list|add|update|remove|outdated|sync` installs, checks and refreshes skills on the [Agent Skills](https://agentskills.io/specification) format; Hand needs no Node and no `npx skills`, and its lock is the one `npx skills` reads.

**Scopes.** `hand skills` acts on one scope, chosen by the flag or by where it runs:

| Scope | Flag | Lands in | Lock and subscription | Reaches |
|---|---|---|---|---|
| project (default) | none in a checkout, `--project NAME` elsewhere | `<checkout>/.agents/skills/<name>`, one root | `<checkout>/skills-lock.json`, `<checkout>/.agents/skills/skills.json` | whoever checks the repo out, so every worker attempt of that project |
| fleet | `--fleet` | `.claude`, `.agents`, `.grok`, `.pi` under the fleet home | `<fleet home>/skills-lock.json`, `<fleet home>/skills.json` | the supervisor session and `hand` itself |
| user | `--user` | the same four roots under `$HOME` | `~/.agents/skills-lock.json`, `~/.agents/skills.json` | every harness process on the machine |

Inside a git checkout the scope is that project. In the fleet home, which is not a checkout, `hand skills` without a flag refuses and lists the fleet's projects; `--project NAME` acts on the checkout the fleet registered for it. A project skill is committed with the repo, and Hand refuses to add, update or remove one whose folder is dirty in git (uncommitted or untracked changes): commit or discard them first. An attempt's worktree is a checkout of the project, so a committed skill is in its working directory when the worker starts; Hand does not say which harness loads `.agents/skills`.

**Source.** `hand skills add NAME` copies `skills/NAME` from `atqamz/skills`. A `PATH` is a folder holding `SKILL.md`; a `URL` is a git repository whose root is the skill. Hand copies, never links, and stamps `managed-by: hand` into the copy's frontmatter `metadata`.

**Validation.** `add` and `update` refuse, naming the field, a source that breaks the specification, and never rewrite its body: frontmatter present; `name` 1-64 lowercase letters, digits and single hyphens, equal to the folder name; `description` 1-1024 characters; `compatibility`, when present, 1-500; `metadata`, when present, a block map with one `key: value` per line (a flow map such as `metadata: {...}` is refused, because Hand writes its marker into that block); `SKILL.md` under 500 lines.

**Lock.** `skills-lock.json` is the vercel-labs/skills version 2 lock: per skill the `source`, `commit`, `skillPath` and a `computedHash`, the SHA-256 of the installed folder as its README ("Lock File Content Hash") defines it (CRLF to LF in text files, paths sorted by their UTF-8 bytes, `.git`, `__pycache__`, `__pypackages__` and `metadata.json` left out, and a symlink hashed as the file or folder it points to, unless it is broken, loops or leaves the skill folder). A project lock records a local skill's `source` relative to the lock (`./` inside it, `../` outside, `/` separators), as `npx skills` writes it, so a committed project lock holds no machine path; Hand resolves it against the checkout, which holds the lock, when it reads; an entry another tool wrote relative in a fleet or user lock resolves against the fleet home or `$HOME`. Entries written by other tools are kept as they are, and a lock of another version is refused. A skill is Hand's when it has an entry and its `SKILL.md` carries the marker. What the lock has no field for stays in Hand's folder: the hash of an `update` swap in progress, and the lock file Hand holds while it writes (`.agents/skills/` in a fleet or user scope, `<git dir>/hand-skills/` in a project, so a checkout gains no stray file).

**Subscription.** `add` subscribes the scope to a skill: it writes `source` and `ref` into the scope's `skills.json` beside the lock entry, and `remove` deletes both. The subscription says what to follow and whom to trust; the lock says what is installed. A project's pair is committed with the repository.

**Sync.** `hand skills outdated` compares each subscription's `ref` with the lock, by the same hash the lock records, and changes nothing: `current`, `behind` (the source moved), `edited` (the copy was touched), `conflict` (both). `hand skills sync` acts on the result by trust. Trust comes from the URL that is fetched and from the subscription, never from the lock alone: an own source is the own skills repository, fetched from its exact `https://github.com` URL (ASCII, case and all) and named as that repository in `skills.json`, which tracks `main`; a local path counts as own only in the fleet and user scopes, and only when `skills.json` names the same path. Own sources are applied automatically after a backup of the previous copy. Any other source, and every entry whose lock and subscription disagree, is third-party; it pins a tag or commit and moves only on a yes: `sync` prints the diff and the commit it resolved and stops, and `sync --yes NAME@COMMIT` applies exactly that commit, named whole and never by a prefix, or refuses and prints the new diff when the ref moved, because a skill steers workers that run with permissions skipped and an update is a supply-chain step. An edited or conflicting copy is never overwritten. `hand update` runs `sync` for every fleet's own skills, after `hand init` has run in every fleet, and reports what is still behind or edited, in the fleet and in each project (not the user scope); a failed sync never fails the update. `outdated` changes nothing, except that reading a pre-version-2 state file moves it into the lock first. `hand skills update NAME` applies a third-party source with no diff, so the yes guard is on `sync` only. A project skill changes through the repository, so its update is a commit a person or a later bump PR makes.

**Drift.** The locked hash says what Hand installed. A copy that no longer hashes to it was edited. Hand never overwrites or deletes an edited copy and never keeps it as a quiet fork: `update` and `remove` refuse it with exit 3, and the edit goes back to the skill's source as a proposal, not into the copy. A skill whose source moved is refreshed by `update`; a source that moved while the copy was edited is a conflict a person settles.

## Decision path

1. Runtime spikes, Orca and then Luvus, chose Luvus on 2026-09-26. It has fenced input that refuses at permission prompts, zero-token event waits, and exact process identity, and it is a 13 MB binary instead of a 556 MB Electron app.
2. Then a focused redesign on an orphan branch against this spec, reusing proven legacy pieces (state machine, fleet memory, watcher, TOON output) rather than designing from zero.
3. The frozen v19 work is reference material: its contracts list exactly what to demand from any runtime (process identity, cessation, safe cleanup, exact input delivery).
